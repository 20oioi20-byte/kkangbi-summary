# NEW-FORM-GUIDE.md — 신규 취합 양식 개발 시작 가이드

> **용도:** 하반기 Makeup 보고 / 중장기전략 보고 / 분기별 센터장 평가 / 해외연수 대상자 선별 /
> 각종 교육 대상자 선별 / 분기별 자금계획 / 컴플라이언스 자료 취합 등 **새 양식을 새 대화창에서
> 만들 때, 이 문서 + 참고할 기존 완성 파일(예: `kkangbi-collect`)을 함께 첨부**하고 시작한다.
> 이 문서 하나로 매번 처음부터 설명하지 않아도 되도록, 회사 공통 규칙 + 지금까지 확정한 설계
> 원칙을 모아두었다.

---

## 1. 이 문서를 쓰는 방법

새 대화를 열 때 이렇게 요청하면 된다:

> "이 가이드 문서 참고해서 [분기별 센터장 평가] 양식 만들어줘. 원본 엑셀/워드 파일 첨부할게."

Claude는 이 문서만 보고도 아래를 바로 이해한다:
- 회사(kt is / KTIS) 저장·보안 규칙
- 문서 작성 규칙(가나다/○/※/괄호 등)과 워드 파일 생성 방식
- 디자인 톤(원본 문서 그대로의 화이트 UI)
- 프로젝트 구조(도메인별 파일 분리로 토큰 절감)
- 주차/기간 산정 기준

## 2. kt is / KTIS 조직 공통 배경

- 소속: **KTIS AICC사업2단 → 사업5팀** (담당자: 강성호 외 팀원)
- 상위 조직에 매주/매월/분기 단위로 보고서를 취합해서 제출하는 구조
- 취합 흐름: **팀원 각자 작성 → 취합담당자(성호님)가 병합 → 팀장 확인 → 상위 제출**
- 이 문제를 자동화하는 것이 "깡비서 취합 모듈"의 목적. 지금까지 "주간보고"를 1호 사례로 완성함.

## 3. 깡비서(KKANGBY) 플랫폼 공통 규칙 (기존 시스템에서 반드시 지켜야 하는 것)

깡비서는 성호님이 이미 운영 중인 통합 업무 플랫폼(캘린더·손익·업무로그·문서지원 등)이다.
신규 양식도 결국 이 플랫폼에 통합되므로 아래 규칙을 반드시 따른다.

### 3.1 저장 규칙 (최우선)
| 규칙 | 이유 |
|---|---|
| **`app_storage`라는 이름/문자열을 코드에서 절대 쓰지 않는다** | 회사 보안장비가 해당 테이블명의 POST 요청을 차단함 |
| 신규 저장 키는 전부 **`rpt_kv`** 테이블에, `ktis_v11__*` 또는 도메인 전용 키 네이밍 | 기존 관례와 통일 |
| `rpt_kv`는 RLS가 걸려 있어 **service_role 키로만 접근 가능** → 클라이언트가 직접 Supabase를 호출하지 않고 **반드시 `/api/storage` 서버 프록시를 경유** (허브 전체 양식 공용 — 양식마다 새 API 만들지 않는다) | anon key로 직접 접근 시 `42501` 오류로 즉시 실패 |
| `/api/storage` 등 데이터 API는 로그인 세션 토큰이 필요 (`apiFetch()` 래퍼 사용) | 회사 데이터 무단 접근 방지 |
| 대용량 데이터(첨부파일 base64, 로고 등)는 **전용 키/전용 파일로 분리** | 설정 묶음 전체가 실패하는 것을 방지 (탭아이콘을 별도 키로 뺀 사례와 동일 원칙) |

### 3.2 팀원 입력 보안 원칙 (이번 프로젝트에서 확정)
- 팀원이 받는 제출 링크는 **추측 불가능한 개인 토큰**을 포함 (`/collect/{요청ID}-{개인토큰}`)
- 그 토큰은 **본인 담당 데이터 행(row)만** 읽고 쓸 수 있어야 함
- 팀원용 화면에는 캘린더/손익 등 다른 앱으로 이동할 수 있는 메뉴를 절대 넣지 않는다 (다른 시스템 진입 경로 원천 차단)

### 3.3 AI 사용 시 모델 규칙
- 서버 프록시로 AI를 호출할 경우, 모델은 `claude-sonnet-4-6`을 쓴다.
- `claude-sonnet-5`는 한글 인코딩이 깨지는 이슈가 실측되어 **깡비서 본체에서 사용 금지**된 상태 — 신규 양식에서도 동일하게 피할 것.
- (참고: 이번 주간보고 취합 모듈은 최종적으로 **AI 호출 없이 규칙 기반 파싱 엔진**으로 전환해 완성함 — 아래 §5 참고. 새 양식도 가능하면 규칙 기반을 우선 검토.)

### 3.4 디자인 톤
- 깡비서 메인 앱(홈/캘린더/손익 등)은 KT 다크 테마(#000, #FE2E36 등)를 쓰지만,
- **문서 취합류 화면은 원본 엑셀/워드 문서 그대로의 화이트 톤**으로 만드는 것이 사용자가 훨씬 편하게 느낀다는 것을 이번에 확인함. → **신규 양식도 원본 문서 형태를 그대로 옮긴 화이트 UI로 시작할 것.** 화려한 카드/탭/그라디언트 지양.

## 4. 이번 프로젝트(주간보고)에서 확정한 재사용 가능 엔진

새 양식이 "취합 → 워드/엑셀 산출물" 구조라면, 아래 엔진을 거의 그대로 재사용할 수 있다.

### 4.1 워드 작성 규칙 엔진 (`collect-docword-rules.js`)
회사 워드 문서의 실제 서식 규칙:
1. 항목 제목(가./나./다.)은 **굵게**
2. `○` 상세 항목은 앞에 **공백 1칸**
3. `○` 하위 `※` 참고사항은 앞에 **공백 2칸**
4. 가→나 항목 사이 **빈 줄 없이** 바로 이어서 작성
5. 제목에 붙는 부연설명 괄호(날짜·금액 등, 예: `요청 (경영지원팀, 약 2억)`)는 **10pt 위첨자**로 축소
6. 단, 센터명·상품명에 **공백 없이 바로 붙는 괄호**(예: `케이뱅크(62)`, `고객센터(3석)`)는 좌석수·코드이므로 축소하지 않고 원래 크기 유지
7. 같은 성격의 반복 항목(예: "소관센터 운영 관련")은 여러 팀원이 써도 **하나의 항목으로 병합**, 개별 내용은 그 아래 ○로 나열

### 4.2 DOCX 생성 엔진 (`collect-docx-export.js`)
- 브라우저에서 **JSZip으로 직접 OOXML(.docx) 조립** — python-docx 등 서버 라이브러리 없이 클라이언트에서 완결
- 표 서식: 1행(대분류 제목) 배경 `#D9D9D9`, 2/4행(실적/계획 헤더) 배경 `#EFEFEF`, 전부 검정 굵은 글씨 중앙정렬
- 우측 상단 **kt is 로고**를 문서 헤더에 실제 이미지로 임베딩(OOXML `w:drawing`)
- **자간 벌어짐 방지**: `autoSpaceDE`/`autoSpaceDN`을 `0`으로, `snapToGrid`를 `0`으로, 문단 정렬은 `jc=left`로 명시 — 이걸 빠뜨리면 워드에서 열었을 때 글자 사이가 벌어져 보임(한글 워드 고질 이슈, 반드시 새 양식에도 적용)
- 파일명 규칙: `{본부명}주간자료_{팀명}_{저장일자}.docx` 형태 — 양식마다 접두어만 바꿔서 재사용

### 4.3 주차/기간 산정 규칙 (`collect-dates.js`)
- **1주차 = 그 달 1일 ~ 그 주 일요일**(1일이 일요일이면 1일 하루만)
- 2주차부터는 **월요일~일요일** 단위
- 마지막 주는 월말에서 자름
- 월 경계를 자동으로 넘기며 주차 이동 가능 (`nextWeekEntry`/`prevWeekEntry`)
- 분기·반기 단위 양식(하반기 Makeup, 분기별 센터장평가/자금계획 등)은 이 주차 엔진 대신 **월/분기 선택 UI**가 더 적합 — 무리하게 주차 엔진을 재사용하지 말고 해당 양식의 실제 주기에 맞는 선택 UI를 새로 설계할 것.

### 4.4 담당자/관리 구조
- 담당자(팀원) 목록은 `숨기기/수정/삭제` 모두 지원하는 CRUD로 관리
- 대상(센터/평가대상/연수대상 등)도 표 안에서 바로 추가·수정·삭제, 순서는 **마우스 드래그로 컬럼 폭 조절**, **▲▼ 버튼으로 행 순서 변경** — 이 UX 패턴은 "명단 관리형" 양식(해외연수 대상자, 교육 대상자, 센터장 평가 등)에 그대로 적용 가능

### 4.5 프로젝트 구조 (허브 + 양식별 폴더, 토큰 절감 원칙)
- 새 양식은 `forms/{slug}/` 폴더 하나를 새로 만든다 (`index.html`, `css/`, `js/`, `docs/CODEMAP.md`). 다른 양식 폴더는 절대 건드리지 않는다.
- 절대 하나의 거대한 HTML 파일로 만들지 않는다. 그 양식 안에서도 도메인이 여러 개면(탭이 여럿 등) `js/*.js`를 도메인별로 분리한다 — 단, 도메인이 실제로 하나뿐이면(Make up처럼) 억지로 쪼개지 않는다.
- **모든 양식이 100% 동일하게 쓰는 것만** `shared/`로 뺀다: 화면 잠금(`shared/auth.js`), 서버 저장 클라이언트(`shared/kv-client.js`), kt is 로고(`shared/logo-data.js`), 공통 CSS 토큰(`shared/base.css` — 버튼/카드/배지 모양만, 색상은 양식마다 자유). 날짜 계산기·문서작성규칙처럼 양식마다 성격이 다른 로직은 공유하지 않는다.
- **용량이 큰 데이터(로고 base64 등)는 반드시 별도 파일로 분리** — 로고를 안 건드리는 수정 작업에서 그 파일을 열 필요가 없게 하기 위함
- 새 양식 작업 시작할 때 반드시: `docs/HUB-CODEMAP.md`(허브 라우팅 표)에서 시작 → 해당 `forms/{slug}/docs/CODEMAP.md`를 참고해서 **수정이 필요한 파일만 읽고 고칠 것**. 다른 양식 폴더나 전체 프로젝트를 매번 다시 읽지 않는다.
- 저장 키는 `ktis_v11__{formSlug}_*` 형태로 양식마다 접두어를 다르게 써서 서로 겹치지 않게 한다.

## 5. 워드/엑셀 자동 취합 방식 — 두 가지 선택지

| 방식 | 장점 | 단점 | 이번에 채택 |
|---|---|---|---|
| **AI(Claude API) 기반 취합** | 팀원이 완전 자유형으로 타이핑해도 정리됨, 유연함 | API 호출 실패/토큰제한/속도 이슈, 결과가 매번 완전히 동일하지 않을 수 있음 | 초기 프로토타입에서 사용 |
| **규칙 기반(JS 파싱) 취합** | 100% 예측 가능, 빠름, 오프라인 동작, AI 호출 비용 없음 | 팀원이 아주 자유롭게 써도 인식하도록 규칙을 잘 짜야 함 | **최종 채택** — 지금 `collect-docword-rules.js`가 이 방식 |

**권장:** 새 양식도 처음엔 AI로 빠르게 프로토타입 → 패턴이 안정되면 규칙 기반으로 전환하는 순서가 효율적이었다. 특히 "분기별 센터장 평가"처럼 입력 항목이 정형화된 양식은 애초에 규칙 기반(또는 아예 구조화된 입력 폼)으로 시작하는 게 낫다.

## 6. 새 양식 작업 시작 시 체크리스트

새 대화를 열고 이 문서를 첨부한 뒤, 아래 순서로 진행하면 빠르다.

1. **원본 파일 공유**: 그 양식의 실제 엑셀/워드/한글 원본 파일 첨부 (구조 분석용)
2. **입력 주체 확인**: 누가 입력하는지 (팀원 전원 / 센터장 개별 / 성호님 단독 등)
3. **주기 확인**: 매주 / 매월 / 분기 / 반기 / 비정기 — §4.3 판단 기준 참고
4. **재사용 여부 확인**: §4의 워드규칙/DOCX엔진/명단관리 UX 중 그대로 쓸 수 있는 것 표시, 새로 짜야 하는 부분만 별도 논의
5. **완성 후**: `forms/{slug}/docs/CODEMAP.md`(주간보고 것 참고)와 `forms/{slug}/docs/README.md`를 만들어 두고, 루트 `docs/HUB-CODEMAP.md`와 루트 `index.html`의 `HUB_FORMS` 배열에 카드 한 줄 추가 (다음 수정 작업 토큰 절감 + 허브 노출용)

## 7. 배포 관련 결정 사항 (2026-07-25 기준, 허브 구조 실제 적용됨)

- **완성된 것부터 순차 배포**하기로 결정. 8개 양식을 다 만든 뒤 한번에 배포하지 않는다.
- 주간보고가 1호, Make up 계획 관리가 2호 배포 대상. 이후 양식은 완성되는 대로 같은 허브(`kkangbi-summary`, `forms/` 하위 폴더)에 추가.
- 신규 양식 추가 시 별도 Vercel 프로젝트/배포 URL을 만들지 않는다 — 이 저장소의 `forms/{slug}/`에 폴더만 추가하면 기존 배포 파이프라인(GitHub push → Vercel 자동배포) 그대로 반영된다.
- 저장은 처음부터 Supabase `rpt_kv`(`/api/storage` 경유)로 시작한다 — 더 이상 `localStorage` 프로토타입 단계를 거치지 않는다.
